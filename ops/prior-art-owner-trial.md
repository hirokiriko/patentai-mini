# OWNER限定の比較試験版（Issue #150 / PR #151）

2026-10-30のOWNER判断で品質①〜③をIssue #152へ未達・保留として移した。
今回の受入はOWNER本人が既存固定URLの通常比較経路を試せること。
配備成功、HTTP200、エラー表示だけを完了にしない。既存の引用・構造・意味検査、
時間・送信・費用上限と不合格・UNKNOWN時の停止を維持する。

## 比較の停止と通常復帰

- 既存Appの非secretサーバー設定 `PRIOR_ART_COMPARISON_ENABLED` だけを使う。
  厳密な文字列 `1` がON。`0`・未設定・その他はOFF。クライアント指定では変更できない。
- 停止は正規のAzure設定更新で値を `0` にし、revisionの反映後、認証下の比較画面と
  `GET /api/cases/{caseId}/analyze` の `enabled:false` を確認する。
  新規POSTは認証・CSRF検査後に503 / `comparison_disabled`で拒否し、予約もAI送信もしない。
- OFFでも既存の保存結果・状態照会・PDF/CSV・原本読取と他機能は維持する。
  GET・再表示・再取得はAIを送らない。失敗表示と旧正常結果は分けて表示する。
- OFFは新規受付の停止であり、実行中処理や課金の即時停止ではない。
  revision更新に先立ち稼働操作を照合し、既存の終端・状態照合・精算経路で収束させる。
  UNKNOWNの予約解放、盲目再送、処理の強制終了は行わない。
- 復帰は停止原因、現在の費用/回数/期限、正規OWNER認証・署名/profileを確認し、
  同じ設定を `1` に戻す。画面/GETの有効状態を確認する。比較はOWNERの明示操作だけで開始する。
  旧正常imageへの通常復帰が必要な場合は、保存データを削除せず既存の復旧手順を使う。

## 通常配備と最小利用確認

1. 同headの対象テスト・lint/type-check/build・独立Localレビュー・必須CIを確認する。
   配備前受入を品質①〜③の合格に読み替えない。失効した研究期限や未使用枠を転用しない。
2. expected headで正規Squash Mergeし、既存Azure workflowでAppと固定Manual Jobの
   同一digestを確認する。Job起動0。旧正常image/configを保持し、現headへ必要な正規束縛を行う。
3. Easy Authの本人制限・直接container入口・Origin・案件境界を確認する。
   ON/OFFはこの承認済み工程の一部。機能ONでも既存検査・費用制限を通す。
4. 対応範囲内の小さな完全架空/公開サンプル1例を通常比較で処理する。
   原稿のテキスト取込後、先行技術文献を直接追加して指定文献比較を開く。
   検索式生成用の旧請求項抽出はこの比較の前提にしない。
   開始前に必要送信数・入出力・費用を固定し、検査を通った結果の表示→保存→再表示と
   代表引用の原文対応、同じ保存結果からのPDF/CSV・試験版表示・再取得AI0を確認する。
5. 実行終端・永続保存・認証付き再読取と常設App/DB/Storage構成を対応させる。
   OFF拒否と既存結果維持を確認後、正常利用できる場合はONで引き渡す。
   全例失敗時は「配備済み・比較利用未成立」と記録し、必要な停止/正常復帰を行う。

既存PDF/CSVのrenderer・保存v1・原本は不変。新しく取得する帳票と画面の共通注意書きに
試験版・原文要確認を表示する。#148の別試用へ比較機能を開放せず、新環境・秘密・IAM・
network・DB migration・依存追加を行わない。固定URLや公開安全な結果以外の認証情報、
原回答、秘密ログ、個人パスはGitHubへ載せない。

## reviewの引用形式

reviewの通信形式v3は各partを順番どおりの完全一致する本文で渡す。
partの連結は元target全文と一致し、各partは一つの文の範囲に収まる必要がある。
part内の根拠は `0|完全一致する引用` の形式で、そのpart内の出現順を指定する
（0始まり、重なりを含む）。区切りは最初の `|` だけで、空白・改行・記号は変更しない。
帰属は本文の `基準側` 等の語を指定し、既存の直前marker選択とscope検査で座標を確定する。
検証済みのmarkerがpart先頭にある場合、markerと直後一文字の「は／の」は構文として
網羅性に数える。技術本文は従来どおりbasisによる網羅を要求する。
独立した引用番号表やtarget全体での出現数計算は不要になる。

原文との完全一致、出現順、UTF16境界、文の範囲、帰属・意味・根拠・保存前検査と
64,000 bytesの応答上限は維持する。旧v1/v2応答の修正による採用や、
不正引用の補修・再送は追加しない。内部の検証済み座標と保存v1の形式は不変。
本変更だけで実AI比較・保存・帳票の受入成功とは扱わず、通常経路で別途確認する。

生成文は各側の主体・動作・条件を文中に明記し、「同じ条件」等への省略を避ける。
照合側は条件の根拠operatorを保持する。`when` の条件末尾が `を超えると` または
`を下回ると` の場合だけ、比較keyでは接続助詞「と」をrelation側の表現と重複させない。
元meaning・引用・bindingは変更しない。閾値・方向・否定・条件集合・only_whenは区別し、
一般の末尾「と」や別表現への同義語変換は行わない。

追加配備時の容量見積もりのため、既存workflowはpush前にimageの展開容量が
8 GiB以下であることを確認する。超過時はpush・配備前に停止する。
これは料金精算や実AI受入の代替ではなく、追加imageの保存量を有限に見積もるための上限。

今回の追加配備は、前月から未精算の配備操作も月間使用数に残す。
既存の月間補足V1（forward 9）は変更せず、署名されたrepair専用補足だけで
forward 10を扱う。月額・jobs・minutes・旧留保は据置とし、前のplanのdigestを照合する。
Localの管理経路が承認・対象コード・一度だけの配備を検査し、このschema追加だけでは
実行を許可しない。補足適用から新imageの稼働まで旧imageの管理対象機能は停止側となる。
新profileの有効化前に配備を完了できない場合は、旧月間planを戻して旧imageを確認する。
新profileの有効化後は、同じ配備の比較OFFを通常の復旧とする。
消費済みforward 10を残して旧上限9へ戻すと旧profileの有効化はできない。
さらに旧imageへ戻す必要がある場合、管理対象機能の停止を維持する復旧となり、
その正常再開まで完了したとは扱わない。旧予約の削除・精算済み扱いで回避しない。

11月へ継続する場合は、別の署名済み月間補足
`ISSUE150_NOVEMBER_REPAIR_MONTH_V1` を使う。前月planのdigestを照合し、
旧操作・未精算予約は残したまま、各予算poolの未使用分だけを引き継ぐ。
11月のbase見積もりは前月以上とし、月額は補足の有限な上限内で別途承認を受ける。
一度設定した11月planの費用枠を増やしたり、この補足を外して制限を回避したりしない。
署名profileと有効期限を必須とし、操作の最大所要時間が期限をまたぐ場合は開始しない。
forward 10から9へ復旧しても履歴を減らさず、既消費が上限を超える場合は停止を維持する。
このコードの追加やLocal検証は、新しい実行権・配備・AI送信の承認ではない。
